The virtual file system behind agent-driven editing

An LLM agent editing code in the cloud is a multi-writer concurrency problem. The VFS is how we solved it.

When an agent edits files in a sandbox while a human watches in their editor, you're running a multi-writer system. The agent writes, the human writes, and both think they own the file. We couldn't hand the agent raw disk access — it would overwrite human work and there'd be no way to undo it.

The answer was a virtual file system: an in-memory tree that all writes flow through, with versioning, diffing and conflict detection built in. Everything the agent does is a patch on top of a version, never a destructive write.

Design: files are version lists

Each file is a list of versions. A snapshot is a map of path → version_id, and snapshots are cheap because the file contents are content-addressed and shared.

// core types, simplified
struct Version {
    id: u64,
    content: ContentAddr,   // deduplicated via sha
    parent: Option<u64>,
    patches: Vec<Patch>,     // inverse patches for undo
}

struct VFS {
    files: HashMap<Path, Vec<Version>>,
    snapshots: Vec<HashMap<Path, u64>>,
}

An agent edit becomes read version N, apply edit, produce version N+1. The human's editor keeps showing version N until they accept the sync; at that point the diff is explicit.

Diff tracking: Myers, at save time

We compute diffs with Myers' algorithm at every save (the same core as git), but we store the patch, not the file. Patches are 5–20× smaller than full files, which matters when you're streaming them to a browser over WebSocket at interactive rates.

On a 10,000-line file, diff computation runs in 2–5 ms. That's fast enough to be synchronous with the save; no background worker, no eventual consistency surprise.

Merge conflicts: the human always wins

The interesting case: the agent rewrites auth.ts while the human is mid-refactor in the same file. Both edits are real. Overwriting either one loses work.

We detect conflicts at the hunk level: if the agent's hunks overlap the human's uncommitted changes, we don't auto-apply. The UI shows the agent's proposed hunks inline as suggestions; the human reviews, accepts or rejects each one. This is the same model as a pull request, but at the granularity of a single file and a single edit.

Conflicts are rare in practice (agents edit in bursts, humans edit continuously), but when they happen, silently resolving them would have been unforgivable. The safety rule: an agent write never lands without a diff the human can see.

Undo that works for both writers

Every patch stores its inverse. Human undo and agent undo are separate stacks, so undoing an agent edit never rewinds the human's own work (and vice versa). After two weeks of agent edits, you can rewind the agent's changes alone, to the state of the repo before the agent existed, as if the agent were a branch.

Sub-100ms sync

The stream to the editor carries binary patches, not events, not snapshots. We batch writes into a microtask flush: whatever the agent touched in the last tick ships as one frame. Backpressure is explicit: if the client is slow, the agent's writes stall rather than queue, which keeps the editor honest.

End-to-end: agent writes a file → diff computed → patched frame shipped → editor renders. Median under 100ms. The agent edits a file and the human sees it appear, character-for-character, at typing speed.

The npm subsystem: dependencies are files too

The same discipline applies to dependencies. When the agent adds a package to package.json, we intercept it: install into a content-addressed cache, reconcile the lockfile instead of letting npm rewrite it wholesale, and diff the result back to the VFS like any other edit. The agent never touches the real npm cache; it gets a sandboxed view that behaves identically.

Lockfile reconciliation deserves its own post, but the short version: we parse the lockfile, compute what the new dependency graph must look like, and emit the minimal patch. No spurious version bumps, no "npm did something weird" mysteries.

Lessons

  • Never let the agent touch raw disk or git in the sandbox. Every write through the VFS is auditable, reversible and diffable; every write around it is a future incident.
  • Patch-level sync is the difference between a demo and a product. Full-file sync over WebSocket dies at the first large file.
  • The human is a concurrent writer. They will both touch the same file eventually; design for it.

The VFS ended up being the least glamorous and most load-bearing piece of the whole IDE.
